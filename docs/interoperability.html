はじめに — なぜ「そのまま」にはならないのか

Excel・ODS（LibreOffice など）・Numbers は、同じものを作る道具ではありません。 見た目が似ているだけで、中身の考え方がかなり違います。

  • Excel は「格子（グリッド）」です。1 枚のシート＝1 枚の巨大な方眼紙。
  • ODS もほぼ格子ですが、OpenDocument にしか無い考え方をいくつか持っています。
  • Numbers は「画用紙（キャンバス）」です。1 枚のシートの上に、 表もグラフも図形も並べて置く。だから 1 枚に表が何枚もあり得ます。

ですから「Excel の機能を Numbers に入れる」のではなく、置き場所があるかどうかが すべてを決めます。置き場所が無いものは、どんなに丁寧に変換しても入りません。 この文書がやっているのは、どこに置き場所が無いのかを一覧にすることです。

「必ず言う」を、どうやって保証しているのか

約束するだけなら誰でもできます。ここでは機械に突き合わせさせています。

  1. 47 の機能を全部入れた 1 冊を用意し、それぞれの形式で本物のファイルとして一度保存します。
  2. そのファイルを開き、別の形式で保存します。
  3. 開き直して、消えた機能を数え上げます。
  4. 消えた機能それぞれについて、その機能を名指しする言葉を含む警告があるかを確かめます。 「表が落ちました」のような曖昧な警告で「配列数式」の消失を言い逃れできないよう、 照合語は機能ごとに 1 つに絞ってあります。

いちばん誤解されやすいところ

「Numbers → Excel は 1 件しか落ちない」は、Numbers が強いという意味ではありません。 この表が数えているのは「いま手元のファイルに入っているものが、行き先で生き残ったか」です。 Numbers ファイルには、そもそも入力規則もピボット表も印刷設定も入っていません。 落ちるものは、Numbers に入るときに落ちきっているのです。

読み方 Excel のファイル（41 機能）を Numbers にして Excel に戻すと、 16 機能になります。実測すると帰り道の警告は 0 件—— 嘘ではなく、そこにはもう失うものが無いのです。 往復のコストは、行きの片道で決まります。

同じ形式に保存し直すとき（いちばん普通の使い方）

実際にいちばん多いのは、変換ではなく「開いて、1 セル直して、同じ名前で保存」でしょう。 ここでの約束は変換より強く、触っていないものはバイトのまま戻すです。

Excel（.xlsx / .xlsm） バイトまで同一（グラフ・テーマ・画像・VBA） 意味は同じ XML に書き直し（条件付き書式・入力規則など） いちばん強い保全
ODS 再梱包はするが、content.xml を作り直すため画像・オブジェクトは繋ぎ直されません 意味は同じ XML に書き直し 中身は残る、絵は繋がらない（警告あり）
Numbers 保全なし。毎回空のテンプレートから作り直します 値・数式・書式・条件付き書式・リンク・メモ・結合など 作り直しなので、元の図形は戻りません

ここが今回いちばん大きな発見でした。テストはずっと「作って、書いて、読む」を確かめていました。 「読んだものを、もう一度書く」は、誰も確かめていませんでした。

今回の点検で見つかったこと

欠陥 5 件と、線引きに判断が要った 2 件です。7 件とも直し、 再発を捕まえるテストを足しました。

1. ピボット表つきの Excel ファイルは、保存すると壊れていた 修正済み

いちばん重い件です。ピボット表の部品には、書き手がいつも自分で書く属性が 15 個あります （updatedVersion・createdVersion など）。ところが読み手の「知っている属性」の一覧には 5 個しか載っていませんでした。残り 15 個は「モデルでは言えない属性」として覚え直され、 次の保存で書き手の分と並べてもう一度書かれていました。

属性が 2 回書かれた XML は規格として壊れています。Excel なら修復を促し、 こちらの読み手はその部品を黙って読み飛ばしていたので、ピボット表は警告もなく消えていました。

そして Excel が書いたファイルも、これらの属性を持っています。 つまり自作ファイルの往復に限らず、Excel で作ったピボット表つきのブックを開いて保存すれば、1 回目で壊れていました。

直し方: 書き手が「この呼び出しで実際に書いた属性名」を集めておき、ファイル由来の属性はそこに無いものだけ足す （RootAttributes）。手で一覧を合わせる方式をやめたのは、今回の欠陥がその記憶違いそのものだったためです。

2. 読めなかった部品を、黙って飛ばしていた 修正済み

上の 1 が「気づかれない欠陥」になった理由がこれです。部品の XML が読めなかったとき、 読み手はただ次へ進んでいました。いまは「この部品が読めなかったので、そこにあったピボット表は飛ばしました」と 部品名つきで言います。Excel を読む処理も、他の形式と同じく警告を返すようになりました。

自作の読み手が自作の書き手を読めても、それは何の証明にもなりません。 ここで「対応している」と言えるのは、この計画から出てこなかったものが同意したときだけです。

Numbers.app 15.3.1書いた .numbers を開き、何が見えるかを答えさせ、保存し直させる
LibreOffice書いた .ods / .xlsx を開き、PDF に変換できるか・要素が残るか
openpyxl書いた .xlsx を読み、同じ値・同じ型になるか（振る舞いの基準としても使っています）
numbers-parser書いた .numbers を独立した実装として読めるか

読み込みも書き出しも、結果に一覧が付いてきます。捨てない限り、見落とすことはありません。
let result = try wb.write(as: .numbers)
for warning in result.warnings {
    print(warning.kind, warning.sheet ?? "-", warning.message)
    // kind は dropped（丸ごと）/ degraded（一部）/ substituted（置き換え）
}
if let suggestion = result.suggestion {
    print(suggestion.message)   // 「この形式では N 件が表せません。◯◯ なら残ります」
}

print(wb.readWarnings)          // 読んだときに言われたこと
