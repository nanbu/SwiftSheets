Chapter 01スコープとライセンス方針

本ライブラリが「何をやるか」と同じ重みで「何をやらないか」を定義する。特にライセンス境界は 実装ルールとしてここで固定し、以降の全章がこれを前提とする。

1.1 目的

Apple プラットフォーム（iOS / macOS / visionOS）および Linux 上で動作する Pure Swift のスプレッドシート 入出力ライブラリを提供する。既存の Swift エコシステムは「読み専用（CoreXLSX）」と「書き専用 （SwiftXLSX ほか）」に分断されており、既存ファイルを開いて編集し、書式を保ったまま保存する ラウンドトリップ編集と、複数形式の相互変換を単一 API で提供するものは存在しない。本ライブラリはその空白を埋める。

1.2 対応マトリクス

形式読み込み新規作成既存編集（保全付き）備考
XLSX ◎ 完全 ◎ 完全 ◎ 完全 基準形式。最優先で品質を担保
XLSM ◎ 完全 ○ 対応 ◎ VBA保持 マクロは不透明データとして保持のみ。実行・解釈しない
ODS ◎ 完全 ◎ 完全 ○ 対応 ODF 1.3 準拠。xlsx⇄ods 変換の片翼
Numbers ◎ 対応 ◎ 対応 ○ 対応 非公開形式のため、表現できない要素は警告で必ず報告（第11章）
CSV ◎ 対応 ◎ 対応 —（概念なし） 値のみ（F1）。UTF-8 は BOM 有無を自動判別、文字コード指定可（第9章）

1.3 非スコープ

  • .xls（BIFF バイナリ） — 旧形式。構造が完全に別物であり、対応しない
  • 数式の評価（再計算） — v2 で独立パッケージ SheetFormulaEval として計画（第5章参照）。v1 は数式の構文解析と方言変換まで
  • VBA マクロの実行・解釈 — セキュリティ境界として恒久的に非対応。保持のみ
  • 暗号化ファイル（ECMA-376 agile encryption 等） — 将来検討。v1 では明示的エラー
  • UI・レンダリング — データモデルと入出力に専念する

1.4 ライセンス方針（実装ルール）

拘束力のある開発規約

本ライブラリは MIT ライセンスで公開する。これを成立させるため、以下を開発規約として固定する。

  • LibreOffice のソースコードは一切閲覧しない。MPL 2.0 はファイル単位コピーレフトであり、移植（翻訳）は Modification に該当するため、閲覧した上での類似実装は汚染リスクとなる。参照してよいのは公開仕様（ODF / OpenFormula）と、LibreOffice が生成した出力ファイル（テストデータとしての .ods）のみ
  • openpyxl のコードは移植しない。API の外形観察とテスト観点の参考に留める。実装は ECMA-376 仕様から書く
  • Numbers 対応は numbers-parser（MIT）同梱の Protobuf 定義を利用する。出所と原ライセンスを NOTICE ファイルに記載する。フォーマット自体の相互運用目的の解析は一般に問題視されにくいが、法的助言ではないため、商用組込み時は利用者側の判断とする旨を README に明記
  • 依存は MIT / Apache 2.0 系のみ許可（ZIPFoundation: MIT、swift-protobuf: Apache 2.0）。コピーレフト系依存の追加は禁止

名称は SwiftSheets（起草時の仮称は SwiftSheets）。Apple のフレームワーク命名（扱う対象が数えられる物は Charts・Contacts・Photos のように複数形）と Swift パッケージの慣習（swift-collections → Collections）に 合わせて 2026-08-22 に複数形で確定し、同日 GitHub に nanbu/SwiftSheets として公開した。

Chapter 02アーキテクチャ概観

4層構造を採る。上位2層（Public API・中間モデル）は形式を一切知らず、下位2層（コーデック・基盤）だけが 各形式の癖を知る。この分離が3形式対応と将来の形式追加の両方を支える。

2.1 各層の責務

層責務禁止事項
L4 Public API人間が書きやすい糖衣。形式自動判別・変換 API形式固有の分岐を持たない
L3 中間モデル値・書式・数式・構造の意味論的保持sharedStrings 索引や XML 断片など「表現」の保持
L2 コーデック中間モデル ⇄ 各形式の双方向射影。損失の警告生成他コーデックへの依存
L1 基盤ZIP・XML・Snappy・Protobuf の機械的処理スプレッドシートの意味を知ること

Chapter 03中間モデル仕様

3形式の最大公約数ではなく「和集合を意味論で正規化したもの」をモデルにする。 設計の要諦は、Numbers のキャンバスモデルを最初から吸収する Sheet = [Table] 構造にある。

3.1 モデル構造

    public var preserved: PreservationStore   // 第6章: 未知要素の保持
}
public struct Sheet: Sendable {
    public var name: String
    public var tables: [Table]         // XLSX/ODS読込時は常に1要素
}

    public var anchor: CellRef          // シート上の左上位置（既定 A1）
    public var cells: [CellRef: Cell]   // 疎行列。空セルは持たない
    public var columnWidths: [Int: Double]
    public var merges: [CellRange]
}
public enum CellValue: Sendable, Equatable {
    case text(String)
    case number(Decimal)                // Numbers の decimal128 精度を保持
    case date(Date)                     // シリアル値は出口で変換
    case bool(Bool)
    case formula(FormulaExpr, cached: String?)  // AST + 最終計算値
    case error(String)                  // "#N/A" 等
    case empty                          // 書式だけ持つセル用
}

3.2 型ポリシー

値種別内部表現設計根拠
数値DecimalNumbers は decimal128 で格納する。Double 経由は往復で精度を失う
日付Date（+ 表示書式は CellStyle）XLSX のシリアル値（1900系・1904系）、ODS の ISO 8601、Numbers のエポックを出口変換に押し込む
数式正規形 AST（第5章）方言（区切り文字・参照記法）は表現であって意味ではない
座標0-based の CellRef(row:col:)A1 記法との相互変換はユーティリティに隔離。bijective base-26 を単体テストで固める
やってはいけない

中間モデルに sharedStringIndex・styleIndex・XML 断片・シリアル日付値などの 「形式の内部表現」を持ち込まない。索引化・シリアル化はすべて各コーデックの書き出し時処理である。 ここが破れると3形式対応は事実上崩壊する。

Chapter 04コーデック抽象化

3コーデックが従う共通契約を定義する。契約は「読み・書き・判別・損失報告」の4点で構成し、 書き出しの戻り値に警告を必ず含める設計とする。

4.1 プロトコル定義

Sources/SheetCore/Codec.swiftpublic protocol SpreadsheetCodec {
    static var format: SheetFormat { get }          // .xlsx / .xlsm / .ods / .numbers / .csv
    static func canDecode(_ container: ZipInspection) -> Bool
    static func read(_ data: Data, options: ReadOptions) throws -> Workbook
    static func write(_ wb: Workbook, options: WriteOptions) throws -> WriteResult
}

public struct WriteResult: Sendable {
    public let data: Data
    public let warnings: [ConversionWarning]   // 損失を黙って落とさない（第6章）
}

public struct ConversionWarning: Sendable {
    public enum Kind { case dropped, degraded, substituted }
    public let kind: Kind
    public let location: CellRef?
    public let message: String   // 例: "Sheet1!C3 の STYLE() は XLSX で表現できません"
}

4.2 形式判別

XLSX / ODS / Numbers は ZIP コンテナ（先頭 PK\x03\x04）であるため、拡張子ではなく アーカイブ内エントリの実在で判別する。判別順序は固定とする。

  1. mimetype エントリが存在し内容が application/vnd.oasis.opendocument.spreadsheet → ODS
  2. [Content_Types].xml が存在 → OOXML。workbook パートの ContentType が …sheet.macroEnabled… なら XLSM、それ以外は XLSX
  3. Index/Document.iwa が存在 → Numbers（ディレクトリバンドル形式は事前に Index.zip を取り出す）
  4. 先頭が PK\x03\x04 でない場合 → BOM 検出と文字コード妥当性検査を行い、テキストとして解釈可能なら CSV / TSV（区切り文字はスニッフィング。拡張子があれば優先 — 第9章）
  5. いずれにも該当しない → SheetError.unrecognizedFormat

4.3 エラー型

public enum SheetError: Error {
    case unrecognizedFormat
    case corruptedContainer(detail: String)      // ZIP/Snappy 層の失敗
    case malformedPart(path: String, detail: String)
    case unsupportedFeature(String)              // 暗号化ファイル等
    case unsupportedVersion(found: String, supported: ClosedRange<Int>)  // Numbers 用
    case formulaSyntax(offset: Int, detail: String)
}
ファサードの動作

Workbook(contentsOf:) は判別 → 該当コーデックの read を呼ぶだけの薄い層とする。 書き出しは wb.write(to:as:) で明示指定を基本とし、拡張子からの推定はコンビニエンスとして提供する。 読み込み形式と異なる形式への書き出し＝変換であり、追加の実装は不要（中間モデルが仲介する）。

Chapter 05数式サブシステム

数式を文字列のまま持ち回ると方言変換で破綻する。v1 の責務は「パースして正規形 AST で保持し、 出口で各方言に書き戻す」まで。評価（再計算）は v2 の別パッケージに委ねる。

5.1 方言差の正規化規則

項目XLSXODS (OpenFormula)正規形（AST）での扱い
引数区切り,;ASTでは配列。出口で選択
セル参照A1 / Sheet2!A1[.A1] / [Sheet2.A1]0-based CellRef + シート名
単項マイナス-2^2 = 4（- が ^ より高優先）パーサの優先順位表で共通化
数式接頭辞=（XML内では無し）of:=ASTに含めない。出口で付与
関数名大部分は共通。固有関数は変換不能正規名（英大文字）で保持。変換不能は ConversionWarning.dropped

5.2 AST 定義（骨子）

public indirect enum FormulaExpr: Sendable, Equatable {
    case number(Decimal)
    case string(String)
    case boolean(Bool)
    case ref(CellRef, sheet: String?, absRow: Bool, absCol: Bool)
    case range(FormulaExpr, FormulaExpr)   // 参照2つを束ねる
    case unary(FormulaOp, FormulaExpr)
    case binary(FormulaOp, FormulaExpr, FormulaExpr)
    case call(name: String, args: [FormulaExpr])
    case unparsed(String, dialect: SheetFormat)  // パース失敗時の退避（下記）
}
パース失敗時のフォールバック

読み込み時に解析できない数式は例外にせず .unparsed(原文, 方言) として保持する。 同一方言への書き戻しなら原文をそのまま出力でき、ラウンドトリップが壊れない。 異方言への変換時のみ ConversionWarning.degraded（キャッシュ値への置換）とする。

v2 の評価器は OpenFormula 仕様が定義する適合レベル（Small → Medium → Large Group Evaluator）に沿って 段階実装する。仕様同梱のテストケース群をそのまま回帰テストに転用できるため、 実装順序も仕様の関数一覧に従う。依存グラフのトポロジカルソートと循環参照検出（#REF! 系エラー）は 評価器側の責務とし、v1 のコードベースには含めない。

Chapter 06ラウンドトリップ保全

「開いて1セル直して保存したらグラフが消えた」を絶対に起こさないための横断ポリシー。 openpyxl が未知要素を破棄する設計であるのに対し、本ライブラリは保持を既定とし、これを差別化点とする。

6.1 忠実度レベルの定義

レベル保証内容適用場面
F1 値忠実セル値・数式・シート構造が等価全形式間の変換で最低保証
F2 書式忠実F1 + フォント・罫線・塗り・表示書式・結合・列幅xlsx⇄ods 変換の目標水準
F3 完全保全F2 + 未対応機能（グラフ・ピボット・VBA等）を無劣化で温存同一形式への上書き保存で必須

6.2 未知要素の保持機構

// Workbook.preserved — 読み込んだが解釈しなかったものの置き場
public struct PreservationStore: Sendable {
    public var sourceFormat: SheetFormat?
    public var opaqueParts: [String: Data]   // 例: "xl/charts/chart1.xml",
                                             //     "xl/vbaProject.bin"
    public var relationships: [String: Data] // .rels は依存ごと保持
}
  • 同一形式へ書き戻す場合：opaqueParts をバイト列のまま再梱包し、参照整合（rels / Content_Types 宣言）を維持する。これが F3
  • 異形式へ変換する場合：opaqueParts は持ち出せない。件数と種別を ConversionWarning.dropped として列挙する
  • Numbers の場合：Protobuf の unknown fields を SwiftProtobuf の保持機構で温存する（読み→同一ファイル書き戻し時のみ有効。第11章）
保持の落とし穴

opaque part が参照するリレーション（rId）を、解釈した part の再生成時に採番し直すと参照が切れる。 既存 rId は不変とし、新規要素は最大値+1 から採番することを全コーデック共通規則とする。

Chapter 07XLSX / XLSM コーデック

基準形式。ECMA-376（OOXML）の SpreadsheetML を対象とし、「Excel が修復ダイアログを出さずに開く」を 合格基準とする。XLSM は XLSX との差分だけを規定する。

7.1 コンテナ構造と必須パート

OPC パッケージ構造book.xlsx (ZIP)
├── [Content_Types].xml        ← 全パートのMIME宣言。宣言漏れ＝開けないファイル
├── _rels/.rels                ← ルート関係。workbook への入口
└── xl/
    ├── workbook.xml           ← シート一覧・definedNames・date1904フラグ
    ├── _rels/workbook.xml.rels
    ├── sharedStrings.xml      ← 文字列プール（書き出し時に構築）
    ├── styles.xml             ← numFmt/font/fill/border → cellXfs 間接参照
    ├── worksheets/sheet1.xml  ← セル本体
    └── vbaProject.bin         ← XLSM のみ。opaque 保持対象

7.2 読み込み規則

  • セル型は t 属性で分岐：s（shared string 索引）／inlineStr／b／str／e／無指定（数値）。日付は型ではなく書式（numFmt が日付系）で判定する
  • 日付シリアル値は workbookPr/@date1904 を必ず参照して基準日を切り替える。1900系では Lotus 互換の「1900年閏年バグ」（存在しない 1900-02-29 = シリアル値 60）を仕様として再現する
  • 数式セルは <f> を AST 化し、<v> をキャッシュ値として .formula(ast, cached:) に格納する
  • 解釈しないパート（charts / pivotTables / drawings / customXml / vbaProject.bin 等）は PreservationStore へバイト保持する（第6章）

7.3 書き出し規則

  1. 文字列セルを走査して sharedStrings プールを構築する。出現1回のみの長文は inlineStr を選択してもよい（プール肥大の回避）
  2. スタイルは値オブジェクト（CellStyle）を正規化ハッシュで重複排除し、fonts / fills / borders / cellXfs の索引を安定順で生成する
  3. ワークシートを行順・列順で直列化する。各行の r 属性、セルの A1 参照、dimension を実データから再計算する
  4. 数式セルに変更が及んだ場合、calcChain.xml を削除し Content_Types の宣言も除去する（残すと Excel が修復を要求する）
  5. PreservationStore の opaque パートを元のパスへ再梱包し、rels と Content_Types の宣言整合を検証してから ZIP を閉じる

7.4 XLSM 差分仕様

項目規定
判別workbook パートの ContentType が …ms-excel.sheet.macroEnabled.main+xml
VBAxl/vbaProject.bin を opaque 保持。解釈・実行・改変 API は提供しない（セキュリティ境界）
xlsm → xlsm 保存vbaProject.bin と関連 rels を無劣化で再梱包（F3）
xlsm → xlsx 保存VBA を破棄し、ContentType を通常版へ差し替える。ConversionWarning.dropped を必ず発行
xlsx → xlsm 保存ContentType 差し替えのみで合法（VBA 無しの xlsm は有効）
「開けない xlsx」の三大要因

(1) Content_Types 宣言漏れ、(2) rels の rId 参照切れ、(3) A1 参照生成の bijective base-26 変換ミス。 この3つで破損報告の大半を占める。いずれも第12章の検証ハーネスで機械検出する。

Chapter 08ODS コーデック

ODF 1.3（ISO/IEC 26300 系列）準拠。構造は XLSX より素直だが、ZIP 梱包規則と RLE 圧縮という ODS 固有の2点を外すとすべてが壊れる。

8.1 コンテナ構造

book.ods (ZIP)
├── mimetype                   ← 無圧縮・先頭エントリ必須（8.2）
├── META-INF/manifest.xml      ← 全ファイルのメディアタイプ登録
├── content.xml                ← 全シートのセル・自動スタイルが単一ファイルに
├── styles.xml                 ← 名前付きスタイル・ページレイアウト
├── meta.xml
└── settings.xml

8.2 ZIP 梱包規則（最重要）

mimetype エントリは非圧縮（Stored）かつアーカイブ先頭に置く。 LibreOffice は ZIP を展開せず先頭バイト列で形式判定するため、deflate で書くと 「ZIP としては正常なのに開けないファイル」になる。 

SheetODS/Writer.swift（要点）let mime = Data("application/vnd.oasis.opendocument.spreadsheet".utf8)
try archive.addEntry(with: "mimetype", type: .file,
                     uncompressedSize: Int64(mime.count),
                     compressionMethod: .none) { pos, size in   // ← .none が肝
    mime.subdata(in: Int(pos)..<Int(pos) + size)
}
// 以降のエントリは deflate でよい

8.3 セルの読み書き規則

  • RLE 展開（読み）：table:number-columns-repeated / table:number-rows-repeated を展開する。ただし空セルの巨大リピート（行末パディング、上限 16,384 等）は展開せず打ち切る。展開するとメモリが爆発する
  • RLE 圧縮（書き）：同一内容の連続セルは repeated 属性へ畳む。読みと書きで対称の処理
  • 値は office:value-type + 型別属性（office:value / office:date-value 等）で書き、表示文字列は子要素 <text:p> に置く。日付は ISO 8601 でシリアル値変換は不要
  • 数式は table:formula="of:=…"。AST から ODS 方言（[.A1] 参照・; 区切り）で emit する（第5章）
  • セル書式は content.xml 内の automatic-styles に生成し、セルから table:style-name で参照する

8.4 検証

合格基準は「LibreOffice が警告なく開き、soffice --headless --convert-to xlsx が成功する」。 ヘッドレス変換は CI に組み込める（第12章）。Excel の ODS 実装は方言があるため、 Excel 生成の ODS をテストコーパスに含めて読み側の耐性を確保する。

Chapter 09CSV コーデック

交換用の最小形式。構造は RFC 4180 を基準に現実方言を受容する。本章の主軸は文字コード方針であり、 「指定がなければ UTF-8（BOM 有無を自動判別）、必要なら任意の文字コードを明示指定」を読み書き共通の原則とする。

9.1 モデル写像

  • 読み込み：1シート・1テーブルの Workbook を生成する。書式・数式構造・結合の概念は形式に存在しないため、忠実度は定義上 F1（第6章）
  • 書き出し：既定ではアクティブシートの既定テーブルのみを出力する。複数シートのブックでは、出力されないシートを ConversionWarning.dropped として報告する（対象シートはオプションで指定可能）
  • 書式・数式の喪失：CSV の定義そのものであるため、セル単位の警告は出さず、ブック単位のサマリ警告1件（「書式と数式構造は CSV では保持されません」）に集約する。警告は出すが、ノイズにはしない
  • 形式判別：CSV は ZIP コンテナではないため、第4章の判別規則に「非 PK データはテキスト妥当性検査＋区切り文字スニッフィングで CSV/TSV と判定（拡張子があれば優先）」の分岐を追加する

9.2 文字コード仕様（本章の核心）

場面指定なし（既定）明示指定
読み込み 先頭バイトを検査する。UTF-8 BOM（EF BB BF）あり → BOM を除去して UTF-8 として読む。BOM なし → UTF-8 として読む。BOM の有無どちらでも追加指定なしで正しく読める。UTF-16 BOM（FF FE / FE FF）を検出した場合は UTF-16 として読む CSVReadOptions(encoding:) に String.Encoding を渡す（.shiftJIS・.japaneseEUC・.utf16LittleEndian 等）。指定時は BOM 自動判別を行わない（ただし .utf8 指定時の先頭 BOM は除去する）
読み込み失敗時 指定（または既定）の文字コードとして不正なバイト列は、黙って文字化けさせず SheetError.malformedPart（バイトオフセット付き）で失敗する。lossy: true を指定した場合のみ置換文字で読み進め、degraded 警告を返す

BOM の使い分け指針

BOM なし UTF-8 の CSV を日本語環境の Excel でダブルクリックすると文字化けする（Excel が レガシー文字コードで解釈するため）。人に配って Excel で開かせるなら includeBOM: true、 システム間連携やプログラムでの取り込みなら BOM なしが原則。この指針は API ドキュメントにも記載する。

9.4 型の扱い

  • 読みの既定は全フィールド .text。暗黙の型推論はしない — 「01234」（郵便番号）が数値化して先頭ゼロを失う、「1-2」が日付化する、という CSV 二大事故を仕様レベルで排除する
  • inferTypes: true 指定時のみ、数値・真偽値・日付（dateFormats で書式指定）を推論して型付きの CellValue にする
  • 書き出し：数値はロケール非依存（小数点 .・桁区切りなし）、日付は ISO 8601 既定（dateFormat 指定可）、真偽値は TRUE / FALSE、数式セルはキャッシュ値（無ければ数式文字列＋ degraded 警告）

Chapter 10Numbers コーデック（読み込み）

非公開の IWA 形式を扱う唯一の章群。読み込みはリバースエンジニアリング済み知見の再実装であり、 技術的には確立している。設計の中心は「バージョン追従を運用として回せる構造」に置く。

10.1 Protobuf 定義の調達と生成

  1. numbers-parser（MIT）同梱の .proto 群と TSPRegistry 対応表を取り込み、出所・原ライセンスを NOTICE に記載する
  2. protoc + protoc-gen-swift で Swift コードを生成し、生成物をリポジトリにコミットする（ビルド時生成にしない — 再現性と protoc 依存排除のため）
  3. 対応表（type 整数 → メッセージ型名）は JSON リソースとして同梱し、コードから分離する。Numbers 新版追従時はこのリソース＋protoの差し替えで完結させる

10.2 デコード規則

  • ディレクトリバンドル（旧保存形式）と単一 ZIP の両方を受理する。バンドル時は内部の Index.zip を実体とする
  • Snappy は生ブロック伸長のみを Pure Swift で自前実装する（フレーミングが独自であるため外部ライブラリの利点がない）。LZ77 系の伸長のみで約100行、依存ゼロ
  • セル実体は TST 系メッセージのタイル（行列を矩形分割したパック形式）に格納される。数値は decimal128 → Decimal へ損失なく変換する
  • 文字列は TableDataList（共有プール）参照。書式・数式文字列も同様の間接参照で解決する
  • 未知フィールドは SwiftProtobuf の unknown fields 保持を有効にし、破棄しない（第11章の書き戻しで使う）
  • シート上の複数テーブルはそのまま Sheet.tables へ写像する（第3章のモデルが受け止める）

10.3 バージョン追従ポリシー

恒常的な運用コスト

Apple は形式の互換性を保証しない。よって (1) README に検証済み Numbers バージョン範囲を明記し、 (2) 範囲外のファイルは SheetError.unsupportedVersion ではなく可能な範囲まで読み進めた上で警告を返し、 (3) Numbers 新版リリース時にコーパス再生成 → proto 差し替え → 回帰テストを回す手順を MAINTENANCE.md として文書化する。読み込み失敗の指標として Metadata/BuildVersionHistory.plist の生成バージョンをエラー情報に含める。

他形式と同格の正式対応とする。v1 の書き出し機能セット（値・数式・書式・構造）を Numbers でも完全に サポートし、非公開形式ゆえに表現しきれない要素は、全形式共通の警告機構で漏れなく報告する。 合格基準は「Numbers が警告なく開き、そのまま編集を継続できる」こと。

11.1 生成戦略 — テンプレート・パッチ方式

オブジェクトグラフをゼロから構築するのではなく、Numbers で作成した最小の空ドキュメントを テンプレートとしてリソース同梱し、そのグラフを差し替える方式を採る。 文書全体の整合（設定・テーマ・スタイル継承の根）はテンプレートが既に持っているため、 実装が触るのはテーブル周辺のサブグラフに限定される。

  1. テンプレートを展開し、全オブジェクトの最大 ID を求める。新規オブジェクトは最大値+1 から採番（既存 ID は不変 — 第6章と同じ規則）
  2. シート数・テーブル数に応じて SheetArchive / TableInfo 系ノードを複製し、参照（Reference メッセージ）を張り替える
  3. セルデータをタイル形式へパックし、文字列・書式は TableDataList プールへ登録する
  4. 数式は Numbers 内部の数式アーカイブ（AST 相当の構造）として生成し、開封直後から再計算可能な状態にする。関数マッピング表に存在しない関数のみ、キャッシュ値表示＋ degraded 警告へフォールバックする
  5. 各 .iwa を Snappy 再圧縮し、ZIP へ梱包。preview.jpg はテンプレートの汎用画像を流用する
  6. 読み込み済みファイルの書き戻し時は、unknown fields を含む元グラフを土台にし、変更セルのみパッチする（保全レベル F3 相当を目指す）

Chapter 14API リファレンス — openpyxl 対応 全一覧

14.1 設計原則

  • 値型と明示的保存 — Workbook は struct。編集は値の変更、永続化は write(to:) のみ。暗黙の副作用を持たない

  • 型付きの値 — openpyxl の「なんでも cell.value」に対し、取得は CellValue enum、代入はリテラル変換（Int / String / Date / Bool / Formula）で受ける
  • 座標は二本立て — A1 文字列（1始まり）と [row, col]（0始まり）の両方を提供。混同事故を防ぐため整数版に 1 始まりは存在しない

B.2 中間モデル（§3 との差分）

本文実装理由
case number(Decimal) のみ.integer(Int) と .number(Decimal) の二本立てopenpyxl の int / float 区別は表示文字列（"1" と "1.0"）に影響し、Stream の相互検証がそれに依存する。Decimal はファイルの数字文字列をそのまま保つ（0.1 が 0.1000…55 にならない）
case date(Date).date(CivilDateTime)（時差なし暦日時）＋ .time(TimeOfDay) / .duration(Duration)表計算の日付はタイムゾーンを持たない。Foundation.Date は CellValue(Date, in: TimeZone) で明示変換
case text / case empty.text（同じ）。空セルは Cell.value == nil で表し .empty は持たない。.richText([TextRun]) を追加Optional が Swift の流儀。書式だけのセルは value == nil のまま cells に存在する
formula(FormulaExpr, cached: String?)formula(FormulaExpr, cached: CellValue?)キャッシュ値には型がある（t="b" / "str" / "e" / 数値）。dataOnly 読み込みがその型を返す

B.8 ODS・Numbers の実装方針（Rev 1.4・P3〜P5）

本文 §10〜§11 からの逸脱（理由つき）
  • Protobuf は SwiftProtobuf ＋ protoc ではなく、依存ゼロの動的ツリー（ワイヤ形式のデコード／エンコードを自前実装し、フィールド番号で辿る）。理由: (1) 外部依存ゼロを全ターゲットで保つ、(2) 未知フィールドの保全（§10.2）が構造的に成立する — 読んだバイト列をフィールド順のまま持ち、触ったフィールドだけ書き換える、(3) protoc / protoc-gen-swift のビルド環境を要求しない、(4) 1,129 メッセージ分の生成コードを抱えない。型安全性は失うため、使うメッセージとフィールド番号は numbers-parser の記述子から機械抽出した JSON リソース（Sources/SheetNumbers/Resources/）から引き、手で書き写さない。
  • Numbers の数式は書き出さない（§11.1・§11.2「◎ 内部表現で生成」は未達）。数式セルはキャッシュ値を書き、degraded 警告を返す — §11.2 の「マッピング不能な関数」の退避規則を全関数に適用した形。理由: 参照実装 numbers-parser 自身が数式アーカイブを書けず（読みのみ）、この Mac には Numbers が無いため新規生成した内部表現を検証できない。
  • 検証の審判: Numbers 実機での開封確認は不可（環境に無い）。自動審判は numbers-parser による読み戻し（§11.3 の「クロス実装検証」）と自前の往復。ODS は LibreOffice ヘッドレス（§8.4）。Excel 生成の ODS コーパス（§8.4）は Excel が無いため未収集。
  • ODS（P3・実装済み）: §8 のとおり自前実装（LibreOffice のソースは閲覧していない — 審判として実行し出力ファイルを観察しただけ）。mimetype は stored で先頭、RLE は読みで展開し末尾の空反復は打ち切り、書きは対称に畳む。結合は number-columns-spanned / rows-spanned と covered-table-cell、日付 / 時刻は ISO テキスト（PT26H 以上は継続時間）、数式は AST の ODS 方言（of:=）。列幅は 2.0 mm / 文字（読み書き同一の定数。LibreOffice 既定の 8.43 文字 = 2.267 cm には合わせない）、行高は pt（use-optimal-row-height="false"、読みでは optimal=true の高さは無視）。罫線は thin / medium / thick = 0.75 / 1.75 / 2.5 pt。列の default-cell-style-name は ColumnDimension.style へ写し、自前スタイルを持たないセルに適用する（LibreOffice は列書式をここに畳む）。表示書式は XLSX コードと number:*-style をトークン単位で双方向変換し、複数セクション（先頭のみ・substituted）、style:map 付き・元号・四半期・分数は General ＋ degraded（データスタイルごとに 1 回）。凍結は settings.xml の Tables マップ、非表示シートは table:display、定義名は named-expressions、注釈は office:annotation、リンクは text:a。ODS → ODS の書き戻しは content.xml を再生成するため図形・グラフは再リンクされない（dropped 警告、Pictures 等は opaque 保持して manifest に再登録）。行グループは読みのみ。数式を持たない .error は文字列になる。検証: LibreOffice ヘッドレスで生成 ODS を xlsx 化して値・結合・凍結・書式・注釈が一致、LibreOffice 産 ODS（同梱コーパス 2 件）を読んで元の xlsx と一致。Excel 産 ODS コーパスは未収集。
  • Numbers 読み（P4・実装済み）: IWA（4 バイトヘッダ＋ Snappy 生ブロック、自前伸長）→ varint 長 → ArchiveInfo → 動的 Protobuf ツリー → オブジェクト ID で解決。Document → Sheet → TableInfo → TableModel → DataStore（タイル・文字列表・数式表・リッチテキスト表）をモデルへ写像: 値（空・数値 decimal128 / double・文字列・リッチテキストは平文・日付 2001-01-01 起点・真偽・継続時間・エラー）、数式は TSCE の後置ノード列を関数表（numbers-parser の functionmap）で XLSX 方言の文字列に戻して FormulaExpr.parse（他テーブル参照は 'シート::テーブル'!A1、失敗時 .unparsed）、結合（formula store の COLON_TRACT → region map の順）、列幅（pt ÷ 5.7 = 文字数）/ 行高、非表示行列、テーブル位置を Table.anchor（20pt × 98pt 格子に丸め）、ヘッダ行列を freezePanes。書式（太字・塗り・表示形式）は読まない（F1 水準。F2 はロードマップ）。バージョン方針は §10.3（tolerant 既定。BuildVersionHistory.plist の最終エントリを sourceInfo.version に載せ、検証済みは Numbers 11〜15 世代）。検証: numbers-parser のテストスイートから 11 文書を同梱し、numbers-parser が読んだ値・数式ツリー・結合・テーブル名・行数と一致（NumbersReaderTests）。
  • Numbers 書き（P5・実装済み、数式を除く）: §11.1 のテンプレート・パッチ方式。テンプレートは numbers-parser 同梱の empty.numbers（MIT。NOTICE 参照）。最初のシート / テーブルはその場でパッチ、2 枚目以降のシートとテーブルは「テーブル固有の型だけ」（TableInfo / TableModel / DataList / Tile / HeaderStorageBucket / 各 FormulaOwner 等、スタイルは共有）をサブグラフ複製して参照を張り替え、UUID を一貫して振り直し、計算エンジンの owner 表と PackageMetadata のコンポーネント登録を追加する。セルはタイル形式（cell storage v5・wide offsets）へパック、文字列は TableDataList へ登録、結合は MergeRegionMapArchive、行高 / 列幅はヘッダバケット、freezePanes はヘッダ行列。非対応: 数式（キャッシュ値＋ degraded）・書式（テーブルごとに 1 件の degraded）・非表示シート（Numbers に概念が無い）。読み込み済みファイルへの書き戻しもこの生成経路を通す（読んだ文書を土台にした F3 パッチはロードマップ）。検証: 自前の往復、numbers-parser による読み戻し（Tests/NumbersParity/verify_with_numbers_parser.py）、LibreOffice の Numbers インポータ（libetonyek）での値一致。Numbers 実機での開封は未確認。
  • 運用: NOTICE（numbers-parser 由来: レジストリ・関数表・記述子由来スキーマ・テンプレート・テストフィクスチャ）と MAINTENANCE.md（§10.3 のバージョン追従手順）をリポジトリ直下に置く。

B.9 堅牢性の上限（Rev 1.5・§12 柱5）

§12 の柱5「malformed コーパス＋ランダム破壊入力でクラッシュ・無限ループ・メモリ爆発がないこと」は 0.2.1 時点で 未達だった。監査で 5 系統の再現（プロセス落ち 4・メモリ無限膨張 1）が取れたため、以下の上限を実装側の決定として固定する。 いずれも「読めない」ではなく「そこで止める」方針で、止めたことは値の欠落なら degraded 警告、 構造の破損なら SheetError で必ず伝える。

忠実度と引き換えにした上限（オーナー承認 2026-08-22）
  • 数式のネストは 64 段まで（FormulaParser.maxDepth）＝ Excel 自身の上限。超える数式は .unparsed として原文のまま保持するので同形式の往復はバイト一致だが、行列挿入時の参照追随と方言変換はそのセルで行われない。 再帰下降 1 段の実測コストは最適化なしで約 7 KB・最適化ありでその数分の一で、64 段は Dispatch が渡す 512 KB スタックと 全リリースビルドに収まる。debug ビルドを 256 KB 以下のスタックで走らせる場合だけは収まらない。
  • A1 座標は走査しながら上限を検査する（CellRef）。列は 3 文字まで、行は 1,048,576 まで。 従来は上限検査がループの後にあり、20 桁の行番号でアキュムレータが桁あふれしてトラップしていた。 <row r="0"> と 1,048,576 超は malformedPart で失敗する（従来は黙って通っていた）。
  • 結合セルが実体化してよいのは 65,536 セルまで（Table.maxMaterialisedMergeCells）。 これを超える結合では、アンカーの罫線と protection の伝播が「既に存在するセル」にしか届かない（openpyxl は プレースホルダを作る）。65,536 以下は openpyxl と同一挙動。あわせて、既定 protection を持つだけの空セルは作らない — <mergeCell ref="A1:CZ2000"/> 一つの 2 KB のファイルが 208,000 セル・554 MB になっていた。 アンカーセルだけは常に作る（ODS ライタが span 属性をそこに載せるため）。ODS ライタ側も同じ上限で、 これを超える結合の covered セルは集合に展開せず幾何で判定する（従来は全面結合の書き出しで OOM kill されていた）。
  • ODS の RLE 展開は 1 文書あたり 1,000,000 セルまで（ODSReader.maxCells）。§8.3 の打ち切りは 「中身のない反復」だけを見ており、値を持つセルの number-columns-repeated × number-rows-repeated は 16,384 × 1,048,576 まで素直に展開していた（1 KB のファイルで 10 分・425 MB 以上・停止せず）。超過分は読まず、 シートごとに 1 件の degraded 警告を返す。1,000,000 は Excel のシート 1 枚（16,384 × 1,048,576）の 0.006% で、そこまで展開して初めて「これは内容ではなく指定だ」と判断できる規模。本来は ReadOptions の 設定値で、利用者が選ぶ理由ができた時点で移す。
  • ZIP は中央ディレクトリの自己申告長を全て検証する。名前長・extra・comment がバッファ外へ出る、 ローカルヘッダのオフセットがファイル外を指す、は corruptedContainer。Numbers 側も同様に length-delimited フィールド長と varint の桁数を検証する。
  • write(to:) はアトミック（Data.WritingOptions.atomic）。開いたファイルへの上書き保存が 本ライブラリの存在理由である以上、書き込み途中の中断が元のファイルを壊してはならない。inode は差し替わる。

B.10 大量データのための実装（Rev 1.5）

§14.11 のとおり v1 は全載せモデルであり、ストリーミングは持たない。そのぶん「1 枚のシートがメモリに載る」ことは 実装の責任になる。監査時点では 20 万セルで RSS 458 MB、100 万セルで 1.5 GB 超と、iOS を対応プラットフォームに 掲げる以上は成立していなかった。原因と対処を記録する。

  • Cell は書式を値で内包しない（496 B → 24 B）。CellStyle は SharedStyle （不変・Sendable な参照型）に載せ、既定書式のセルは何も持たない。稀なハイパーリンクと注釈は CellExtras に畳む。 同じ書式は共有する — XLSX は xf 索引ごと、ODS は自動スタイル名ごと、style(範囲) は クロージャの結果ごとに 1 インスタンス。§3.2 が禁じているのは「ファイル形式の索引（sharedStringIndex・styleIndex）を モデルに持ち込むこと」であって、モデル内部で同じ値を共有することではない。公開 API は不変（cell.style は 今までどおり値を読み書きする）。実測: 60 万セルの構築が 982 MB → 105 MB、全セル書式つき 15 万セルの読み込みが 469 MB → 100 MB。
  • 使用範囲（Table.extent）は逐次維持する。全セル走査の計算プロパティで、 rowCount / row(_:) / rows(in:) / 各ライタが内部で呼ぶため、 for r in 0..<sheet.rowCount { sheet.row(r) } という自然なコードが O(n²) だった。型付きの変更経路 （添字・append・store(_:at:)）で範囲を更新し、cells を直接書き換えられたときだけ 「不明」に落として次回 1 回だけ走査する。60 万セルのシートを 3,000 行なめる操作が 4.49 s → 0.00 s。
  • 一時コピーを作らない。ZIP はパートごとにファイル全体を配列へ写していた（O(ファイル×パート数)）ので withUnsafeBytes でその場で読む。XLSX / ODS のライタは行ごとにセルを詰め直していたので、キーだけをまとめる。
  • 残る上限: ストリーミング読み書きは引き続きロードマップ（§14.11）。1 セルあたりの実測はおよそ 100〜200 B（辞書のオーバーヘッド込み）で、100 万セルで 100〜200 MB。

B.11 API の確定（Rev 1.6・1.0 前の破壊的変更）

1.0 で固定すると直せなくなるものを、この時点でまとめて直した。いずれも本文の意図に近づける変更であり、 本文（§4.1・§14）の記述はここが優先する。

  • 読み込みも結果型を返す: SpreadsheetCodec.read は Workbook ではなく ReadResult（workbook ＋ warnings）を返す。従来は ODS / CSV / Numbers だけが readWithWarnings という 抜け道を持ち、ファサード（Workbook(contentsOf:)）からは読み込み警告が一切見えなかった — §6 の 「損失を黙って落とさない」は読みにも掛かる契約なので、抜け道を廃してひとつの形に揃えた。 Workbook.read(contentsOf:) / read(_:format:options:) が結果型を返し、 利便のための Workbook(contentsOf:) は残す — 警告は Workbook.readWarnings に載って一緒に運ばれるので、 どちらの入口でも黙って消えることはない。
  • 展開量の上限は ReadOptions.cellLimit（既定 1,000,000）。B.9 で内部定数として入れたものを 設定値へ移した（「本来は ReadOptions の設定値」と書いた持ち越しの解消）。
  • 警告は主題を持つ: ConversionWarning.subject（.macros / .objects / .formatting / .formulas / .sheets / .other）。 WriteResult.suggest は書き出し先ではなく失われた物から代替形式を選ぶ （マクロが落ちたなら XLSM、それ以外は XLSX、既にその形式なら提案しない）。従来は xlsx へ書くたびに 「XLSM なら残せます」と言いかねなかった。
  • 形式判別はひとつの実装: SheetFormat.detect(in: ZipInspection) を追加し、各コーデックの canDecode はそれと自分の形式を比べるだけにした。§4.2 の判別順序が二重に書かれている状態を解消。
  • §14.4 の範囲ビューを実装: sheet.range("A1:C3") が RangeView を返す。 行は要求されたときに 1 行ずつ作られ、セルはテーブルと共有する（値の二次元配列を作るのは .values を呼んだときだけ）。 スナップショットであり、後からシートを編集してもビューの見え方は変わらない。
